# Codex 任务：生成检测器数据流与接口说明文档

## 硬约束（违反即失败）

1. **只读**：不允许修改、删除任何现有文件，只能读取代码和文档。
2. **只生成一个文件**：`src/tushenghao/docs/dataflow-interfaces.md`（`docs/` 目录已存在，直接放里面）。
3. **不做 git 操作**：不 commit、不 push、不 merge、不切分支。

## 背景

- 仓库 `campus-marker-opencv-assignment`，当前分支代码即最新状态（含 112 恢复修复）。
- 检测器主体代码在 `src/tushenghao/`：`lib/`（各模块实现，头文件与 `.cpp` 同目录）、`include/mark/`（公共类型）、`app/`（主流程）、`config/`（YAML 配置）。
- **读者是项目作者本人，但对检测器代码细节不熟悉**（大部分由 AI 生成）。文档目标是让他彻底搞懂数据流动和接口契约，不是算法数学推导。
- **不要假设读者"已经懂了"**：每个接口从零讲起——结构体里有什么字段、谁填充、下游谁用。

## 文档结构（参照 `src/tushenghao/submissions/REPORT.md` §1 的风格，中文写作）

### 1. 系统概述
- 输入是什么、输出是什么、一句话架构（模块化流水线）。

### 2. 四点语义契约
- MARK 的四个几何语义角点定义、LT/RT/RB/LB 固定顺序、严格输出规则（四角可信+方向可信+几何合理才输出，否则 empty）。

### 3. 流水线阶段详解
对每一帧，**按执行顺序**列出每个阶段，每个阶段必须包含：
- **实现文件**：哪些 `.cpp/.hpp`（精确到文件名）
- **输入**：数据结构名 + 关键字段（字段含义一句话）
- **输出**：数据结构名 + 关键字段（字段含义一句话）
- **关键参数**：本阶段用的 YAML 参数（参数名、当前值、所在配置文件）

### 4. 核心接口定义
以下结构体逐个拆解，每个字段三问：**含义是什么、谁填充、下游谁用**。
- `Detection`
- `FrameResult`
- 其他在模块间传递的关键结构体（按实际代码列出）

### 5. 112 恢复路径
- 触发条件：旧路径失败后，恢复路径按什么顺序尝试（注意：实际顺序不是简单的 A→B→C1，**以 `corner_edge_fit.cpp` 的 `FastRecovery` 实现为准**，把真实顺序写清楚）。
- 每条路径一句话说明机制和触发条件。

### 6. 已知占位 / 未确认项（诚实清单）
以下已知事实**直接写入文档**，不要重新推导：
- `Detection` 的 `category` 当前为 `Unknown`，`confidence` 为空，`marker_code` 为空——下游不得当作有效证据使用。
- `FrameResult` 的时间源当前为 `Unknown`——时间戳字段已预留但未填充真实值。
- 不确定的地方明确标注"未确认"，**禁止猜测**。

## 写作要求

- 以代码为准，不以旧文档为准。如代码与 `submissions/REPORT.md` 描述不一致，以代码为准并在文档中注明差异。
- 重点是"接口里有什么、装什么、后面用啥"，算法内部数学细节一句话带过(给到大致位置即可，关键函数应提及)或跳过。
- 每个阶段标注其在 `app/main.cpp`（或实际主循环文件）中的调用位置。
- 文档长度不限，但拒绝水分：每个字都要么是接口事实，要么是数据流转关系。
